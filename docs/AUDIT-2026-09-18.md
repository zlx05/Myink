# 写作阻断与台账/召回审查报告

2026-09-18。针对四个报告的现象做取证式排查：写作按钮点不了、台账的人物状态与事件不足、设定实体有问题、事件召回需要降级方案。

结论：**四项全部成立**。其中第 1 项已定位到根因并在真实网关上复现；第 2、3、4 项有代码与数据库双重证据。本报告只做取证，未改动任何代码。

## 1. 写作点不了

### 根因

网关在确认流是否存在**之前**就把响应头刷出去了。

[gateway/internal/handlers/sse.go:41-46](../gateway/internal/handlers/sse.go#L41-L46)：

```go
c.Header("Content-Type", "text/event-stream")
c.Header("Cache-Control", "no-cache")
c.Header("Connection", "keep-alive")
c.Header("X-Accel-Buffering", "no")
c.Writer.Flush()          // ← 200 OK 在这一行已经被提交给客户端
```

此后 [sse.go:91-93](../gateway/internal/handlers/sse.go#L91-L93) 想表达「通道已过期」：

```go
case errors.Is(err, sse.ErrStreamGone):
    c.AbortWithStatusJSON(http.StatusGone, gin.H{"error": "sse_stream_expired", ...})
```

`AbortWithStatusJSON` 里会调用 `WriteHeader`，但响应已经提交，这行**不会生效**；JSON 体照常写出去，状态码仍是 200。

而 [sse.go:24 `gin.New()`](../gateway/internal/handlers/middleware.go)（未挂 Logger 中间件）意味着 gin 那句 `superfluous response.WriteHeader call` 警告也不会出现在日志里 —— 这也是为什么 `docker logs aiink-gateway` 只有一行启动日志，排查时完全没有线索。

### 复现（已执行）

用 dev JWT 直接打真实网关，两个用例：一个已完结且 Redis 流已过期的任务，一个完全不存在的任务。

```bash
curl -sS -i --max-time 8 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: text/event-stream" \
  http://localhost:8080/api/v1/tasks/00a7a719-5bb5-4452-ba3f-2ff9c26573af/events
```

两个用例返回完全一致：

```
HTTP/1.1 200 OK                      ← 期望是 410 Gone
Cache-Control: no-cache
Connection: keep-alive
Content-Type: text/event-stream
X-Accel-Buffering: no
Transfer-Encoding: chunked

{"error":"sse_stream_expired","hint":"fallback_get_snapshot"}
```

### 前端如何被这段响应带偏

[web/src/lib/sse.ts:159](../web/src/lib/sse.ts#L159) 只对 410 做特判：

```ts
if (res.status === 410) { ... return { reason: 'expired', status: 410, body } }
```

200 走不进去，于是继续往下读 body。那段 JSON 没有 `data:` 前缀、也没有 `\n\n` 终结符，`takeFrames` 切不出任何帧，`reader.read()` 立刻 done，落到 [sse.ts:205](../web/src/lib/sse.ts#L205)：

```ts
return { reason: terminalSeen ? 'terminal' : 'eof' }   // → 'eof'
```

[web/src/hooks/useTaskEvents.ts:276-283](../web/src/hooks/useTaskEvents.ts#L276-L283)：

```ts
case 'network':
case 'eof':
  setPhase('reconnecting')
  attempt += 1
  const delay = Math.min(8000, 1000 * 2 ** Math.min(attempt - 1, 3))
  await new Promise((r) => setTimeout(r, delay))
  continue                     // ← 无上限、且从不查快照
```

这个分支有两个结构性问题：

1. **没有重试上限**，`attempt` 只用来算退避，涨到 4 以后延迟封顶 8 秒，循环永远继续。
2. **从不调用 `fetchSnapshot`**。对比 `case 'terminal'`（[useTaskEvents.ts:248-266](../web/src/hooks/useTaskEvents.ts#L248-L266)）会先查数据库快照再决定是否接受终态 —— 这个判据在 `eof` 分支完全缺失。也就是说：**只要 Redis 流没有终态帧，数据库里任务早就 done 了也救不回来。**

于是 `phase` 永久停在 `reconnecting`。

### 为什么按钮会变灰

[web/src/pages/WorkspacePage.tsx:529-535](../web/src/pages/WorkspacePage.tsx#L529-L535)：

```ts
const taskInFlight = Boolean(activeTaskId) && (
  taskIsCreating
  || task.status === 'awaiting_review'
  || taskPhase === 'connecting'
  || taskPhase === 'live'
  || taskPhase === 'reconnecting'      // ← 永久为真

```

→ 作为 `taskBusy` 传给 [WorkspacePage.tsx:747](../web/src/pages/WorkspacePage.tsx#L747) → [GenerationPanel.tsx:57](../web/src/components/GenerationPanel.tsx#L57) `controlsBusy` → 五个写按钮全部 `disabled`（[GenerationPanel.tsx:182](../web/src/components/GenerationPanel.tsx#L182)、[193](../web/src/components/GenerationPanel.tsx#L193)、[202](../web/src/components/GenerationPanel.tsx#L202)、[212](../web/src/components/GenerationPanel.tsx#L212)、[248](../web/src/components/GenerationPanel.tsx#L248)），包括「写下一章」「自动 / 手动确认 Plan」「重写本章」「发起批次」。

### 为什么现在必然触发（而不是偶发）

三个条件同时满足：

1. **Redis 里 `queue:sse:*` 一个键都没有。** `docker exec aiink-redis redis-cli --scan --pattern 'queue:sse:*'` 返回空。流在任务终态后 TTL 1 小时（[gateway/internal/sse/stream.go:24](../gateway/internal/sse/stream.go#L24)），而库里所有任务都是 09-15 ~ 09-17 结束的，早已过期。

   ```
   键空间只剩：rate:cost:2026-09-16 / rate:cost:2026-09-17 / queue:heartbeat:323aa1290c6f-1
   ```

2. **恢复 `activeTaskId` 时不看任务状态。** [WorkspacePage.tsx:482-503](../web/src/pages/WorkspacePage.tsx#L482-L503) 用 `latestGenerationTask` 选「最新的生成任务」，而 [web/src/lib/taskChapter.ts:48-50](../web/src/lib/taskChapter.ts#L48-L50) 只按 `task_type` 过滤，**完全不管 `status`**：

   ```ts
   export function latestGenerationTask(tasks: TaskSummary[]): TaskSummary | null {
     return tasks.find((task) => task.task_type === 'chapter_generate' || task.task_type === 'batch_generate') ?? null
   }
   ```

   对比同文件 [taskChapter.ts:52-62](../web/src/lib/taskChapter.ts#L52-L62) 是有一个带 `ACTIVE_GENERATION_STATUSES` 过滤的版本（`latestActiveGenerationTask`）—— 但这一处没用它。

   所以**不需要 sessionStorage**：只要选中任意一章（该章存在已完结的生成任务），就会把 `activeTaskId` 设成那个 done 任务，死循环立刻开始。

3. 于是现在**每一本有已完结任务的书、每一章，点开即锁死**。

### 佐证：API 从来没收到过写作请求

`docker logs -t aiink-api` 过滤掉 `/openapi.json` 健康检查后，用户最后一次活动是 `2026-09-18T02:24:38`，全部是 GET（`/chapters`、`/tasks`、`/graph`、`/entities`、`/characters`…）。**没有任何一次 `POST .../generate` 到达后端** —— 与「按钮 disabled、onClick 从未触发」完全吻合。

### 附带的两个小问题

- `setPhase('live')` 在整个 `useTaskEvents.ts` 中**从未被调用**，`'live'` 是死枚举值。健康的长连接期间 `phase` 一直是 `'connecting'`。
- 网关硬超时 `sseMaxDuration = 30 * time.Minute`（[sse.go:19](../gateway/internal/handlers/sse.go#L19)）到期后正常关流。如果此时任务在数据库里仍是 `running`，前端进 `eof` 分支后同样是无限重连 —— 这条路径**即使网关不修也可能自己触发**，只是需要任务存活超过 30 分钟。

### 修复方案（未实施，供选择）

**方案 A：网关先探测再决定响应（推荐）**

在写响应头**之前**先 `Exists` 检查 Redis 流键，不存在就直接 `c.AbortWithStatusJSON(410, ...)` 返回，把现有的 410 语义真正落地。改动集中在 [sse.go:40-46](../gateway/internal/handlers/sse.go#L40-L46) 与 [stream.go:55-63](../gateway/internal/sse/stream.go#L55-L63)（`Replay` 里已有一模一样的 `Exists` 检查，可以复用/前置）。

- 优点：语义正确，前端现有 `case 'expired'` 分支原样可用；`fetchSnapshot` 会把 DB 里的 done 状态拉回来，一切自愈。
- 代价：需要重建 gateway 镜像。
- 注意：即使做了 A，`eof` 分支仍然没有上限和快照兜底，30 分钟超时那条路径还在。

**方案 B：前端兜底 + 重试上限**

在 [useTaskEvents.ts:276-283](../web/src/hooks/useTaskEvents.ts#L276-L283) 的 `eof`/`network` 分支里查一次快照；若 DB 状态已是终态则 `setPhase('terminal')` 收尾，同时给 `attempt` 加重连上限（超出则 `setPhase('error')`）。

- 优点：只动前端，能同时覆盖 410 缺失和 30 分钟超时两条路径。
- 代价：治标；网关仍然在发一个语义错误的 200。

**方案 C：A + B（推荐）**

网关恢复真正的 410，前端同时加兜底与上限。两条独立的保险，任一侧回退都不会再次锁死。代价是要重建 gateway 与 web 两个产物。

**另外建议一并修的（无论选哪个方案）**

- [WorkspacePage.tsx:482-503](../web/src/pages/WorkspacePage.tsx#L482-L503) 改用 `latestActiveGenerationTask`，让已完结任务不再被恢复成 `activeTaskId`。这能消掉大部分触发面。
- 给 `gin.New()` 挂上 Logger（或至少 `Recovery`）中间件，否则这类「响应头已提交」的问题在日志里永远看不见。

### 验证计划

1. 单测：`useTaskEvents` 的 `eof` 分支——mock `openSSE` 恒返回 `eof`，断言在 N 次后收敛到 `terminal`/`error` 而不是无限 `reconnecting`。
2. 网关集成：对不存在的 task_id 打 SSE，断言状态码为 410（当前是 200）。
3. 端到端：打开一个有已完结任务的项目，选中该章，断言「写下一章」按钮 `disabled === false`。
4. 回归：确认正常的实时写作（任务进行中）流程不受影响——流转节点、产物流式、审核放行。

## 2. 台账：人物状态与事件

### 2.1 事件是只写不读的

`Event` 模型存在（[src/aiink/models/memory.py:75](../src/aiink/models/memory.py#L75)），worker 也确实在写。数据库现状：

```
 深渊天梯  | 13
 暗火      |  9
 万古魔尊  |  3
 其余 6 本 |  0
```

但用户**永远看不到它们**：

- **没有 API 路由。** [src/aiink/api/main.py:45-56](../src/aiink/api/main.py#L45-L56) 注册了 12 个 router（auth / book / tasks / candidates / chapters / lessons / style / settings / environment / genre / global_audit / rankings），没有 events/memory/lore 相关的。`grep -rn "Event" src/aiink/api/routes_book.py` 零匹配 —— [routes_book.py:41](../src/aiink/api/routes_book.py#L41) 的 import 列表里有 `AgentRun, Character, Entity, Faction, Foreshadow, Location`，**没有 `Event`**。
- **没有 UI。** 前端页面上出现的「事件」字样全部无关：`NewProjectPage.tsx` 的「卷末不可逆事件」、`ChapterPlanPanel.tsx` 的「预期事件」、`LorePage.tsx` 的「卷末事件」。

也就是说，从抽取节点到落库这一段是通的，但**读回来这一半完全没有实现**。

### 2.2 人物状态：底子好，但被压平了

这部分的存储设计其实是**对的**。[src/aiink/models/memory.py:28-50](../src/aiink/models/memory.py#L28-L50)：

```python
class CharacterState(Base, UUIDPkMixin, TimestampMixin):
    """人物状态台账（追加式，只追加不覆盖，当前状态 = 按 chapter_seq 最近有效行，§7.7）。"""
    chapter_seq:    Mapped[int]
    field:          Mapped[str]        # 受 CheckConstraint 约束的枚举
    old_value:      Mapped[str | None]
    new_value:      Mapped[str | None]
    source_chapter: Mapped[int]
    confidence:     Mapped[float]
    valid_from:     Mapped[int | None]
    valid_to:       Mapped[int | None]
```

**完整的变化历史都在库里**：哪一章、从什么变成什么、置信度多少、有效性区间。

问题出在取数函数 [src/aiink/memory/repository.py:98-118](../src/aiink/memory/repository.py#L98-L118)：

```python
def get_character_state(session, project_id, character_id, chapter_seq) -> dict[str, str]:
    ...
    state: dict[str, str] = {}
    for r in rows:            # 同一 field 只取最近一条
        if r.field not in state:
            state[r.field] = r.new_value or ""
    return state
```

返回类型是 `dict[str, str]` —— **字段名 → 最新值**。`old_value`、`source_chapter`、`confidence`、`valid_from/valid_to` 全部在这一步丢掉。

后果有两层：

- **提示词侧**：模型只看到「境界：筑基三层」，看不到「上一章还是练气九层」这类**变化本身**。而网文写作里「角色刚突破」往往比「角色当前是筑基」更关键。
- **界面侧**：即使要补一个状态时间线，这个函数也拿不出数据 —— 得绕开它直接查表。

另外，快照的取样范围也窄。[src/aiink/memory/recall.py:162-177](../src/aiink/memory/recall.py#L162-L177) 只遍历 `participants[:_MAX_ENTITIES]`（上限 12）。代码意图是「只有本章出场人物才可能有状态快照」，但**这个前提不成立**——`participants` 实为全书人物按名字字典序的前 12 人，与本章出场无关（见第 4 节更正）。

### 修复方向（未实施）

1. 新增 `GET /projects/{id}/events`（可按 chapter 区间、人物名、importance 过滤），前端在「设定」页补一块事件台账。
2. 新增 `GET /projects/{id}/characters/{cid}/state-history`，直接读 `character_states` 表返回 `[{chapter, field, old_value, new_value, confidence}]`，界面上画成变化时间线。
3. 让 `get_character_state` 的调用方（[prompts.py](../src/aiink/workflow/prompts.py)）在渲染时带上 `old_value` 与 `source_chapter`，例如「境界：练气九层 → 筑基三层（第 7 章）」。

## 3. 设定实体

### 结论：功能死路

`RetrievedContext.entity_snapshots`（[src/aiink/schemas/contract.py:245](../src/aiink/schemas/contract.py#L245)）这个字段名有误导性。它**确实**被提示词消费，共四处：

- [prompts.py:306](../src/aiink/workflow/prompts.py#L306)
- [prompts.py:414](../src/aiink/workflow/prompts.py#L414)
- [prompts.py:447](../src/aiink/workflow/prompts.py#L447)
- [prompts.py:526](../src/aiink/workflow/prompts.py#L526)（渲染为「【人物状态快照】」）

但**填充来源只有 `Character`**。[src/aiink/memory/recall.py:162-177](../src/aiink/memory/recall.py#L162-L177)：

```python
if participants:
    for name in participants[: _MAX_ENTITIES]:
        ch = repo.get_character(session, project_id, name)
        if not ch:
            continue                       # ← 势力/地点/物品名在这里被静默丢弃
        ...
        snapshots.append({
            "character_id": str(ch.id), "name": ch.name, "realm_cap": ch.realm_cap,
            "state": state, "personality": ch.personality, "relations": relations,
        })
```

查的是 `repo.get_character`（人物表），字段全是人物专属（`realm_cap` 境界、`personality` 性格）。`Entity` 行（`Faction` 势力 / `Location` 地点 / 物品）查不到就 `continue`，**静默丢弃，没有任何日志**。

在 workflow 目录下 `grep -rn "Entity"` **零匹配**，确认实体数据从未进入生成链路。它们只在 `/entities` 这个只读接口上露面（`routes_book.py:279`），供「设定」页展示。

### 修复方向（未实施）

要么在 `recall.py` 里补一条 `Entity` 的取样分支（用 `Entity` 的字段渲染：类型、描述、当前归属），要么至少把这段静默丢弃改成显式记录，避免以后继续误判。**注意**：改动会直接影响四个节点的提示词内容，属于会改变生成结果的改动，需要单独评估与回归。

## 4. 事件召回降级

### 结论：默认配置下几乎是空转，且是静默的

召回入口 [src/aiink/memory/recall.py:294-375](../src/aiink/memory/recall.py#L294-L375) 是双腿 RRF 融合。逐条看默认（`EMBED_ENABLED=0`）下的实际行为：

**向量腿 —— 静默失败。**

```python
try:
    emb = get_embedder().encode([query_text])[0]
    ...
except Exception as exc:
    logger.warning("向量腿召回失败，降级为关键词腿/纯关系: %s", exc)
```

[embedder.py:94-98](../src/aiink/memory/embedder.py#L94-L98) 的 `_DisabledEmbedder.encode` 直接 `raise RuntimeError`，被上面这个 `except` 吞掉，只留一行 warning。**用户侧完全无感知。**

**关键词腿 —— 依赖 `participants`，空了就整条腿没了。**

```python
terms = _terms(participants)
kw_ids = _keyword_event_leg(session, project_id, terms)
```

[`_terms`](../src/aiink/memory/recall.py#L326) 在 `participants` 为空时直接返回 `[]`，[`_keyword_event_leg`](../src/aiink/memory/recall.py#L326) 又对空 terms 返回 `[]`。

**更正（2026-09-18 复核）：`participants` 不是来自章节计划。** 它来自 [nodes.py:620](../src/aiink/workflow/nodes.py#L620) 的 `state["characters"][:12]`，而 `characters` 在 [nodes.py:595](../src/aiink/workflow/nodes.py#L595) 由 `get_all_characters` 填充，后者按 `Character.name` 排序（[repository.py:67-70](../src/aiink/memory/repository.py#L67-L70)）——即**按名字字典序取全书前 12 人**，与本章出场无关。

这比「依赖 plan 的 participants」更糟：不是「本章没排人 → 腿空」，而是**腿一直都在跑，只是跑在一份和本章不相干的名单上**。只有全书零人物时该腿才真正为空。同一个 `participants` 也是台账状态快照的取样来源（见上文），所以这条同时解释了第 2 节「只有本章出场人物才有快照」为什么在实现层站不住。

**双腿全空 → 直接短路返回。**

```python
if not legs:
    return {}          # ← 丢掉的是「额外命中」，不是全部事件
```

**更正（2026-09-18 复核）：这里的「一条事件都召不回来」是错的。** `events_out` 在调用 `_hybrid_recall` **之前**就已经由 `get_recent_events(limit=10, before_chapter=chapter_seq)` 填好了（[recall.py:134](../src/aiink/memory/recall.py#L134)），`return {}` 丢弃的只是混合召回**额外补充**的那部分。准确的说法是：**只有按章节号最近的 10 条，没有任何针对性检索**——这仍然是个真问题（近期无关事件照样占满配额、历史相似事件进不来），但不是「零召回」。

真正成立的是后半句：无论哪条腿，调用方都拿不到状态，**无法区分「确实没有相关事件」和「整个召回通道瘫了」**。

**第 1 章从不召回。** 调用点 [recall.py:207-211](../src/aiink/memory/recall.py#L207-L211)：

```python
if prev and prev.summary:
    recall_stats = _hybrid_recall(...)
else:
    recall_stats = {}
```

没有前一章就没有召回。对第 1 章这是合理的，但它意味着降级设计必须覆盖「无 prev」的路径。

**`embeddings` 表是空的 —— 这是最要命的一条。**

```
 level | count
-------+-------
(0 rows)
```

即使把 `EMBED_ENABLED` 打开，也**没有任何东西可以匹配**——因为历史数据从来没有建过索引，也没有 backfill 脚本。开开关是个空动作。

**更正（2026-09-18 复核）：写入侧是接好的，不是「从来没建过索引」。** [`_index_embedding`](../src/aiink/workflow/nodes.py#L1455-L1471) 确实被调用；它静默失败的原因是 `get_embedder().encode()` 在 `EMBED_ENABLED=0` 下抛 `RuntimeError`，与读侧同一个 `except` 吞掉。所以准确的描述是：**写侧通路存在但默认配置下必然失败且无人知晓**，历史数据（开关打开之前写入的事件）也确实没有索引。两者都需要 backfill，但根因是「静默」而不是「缺失」。

**关键词腿没有索引。** [recall.py:326](../src/aiink/memory/recall.py#L326) 的注释自己承认：

```python
"""关键词腿：事件摘要 ILIKE 命中任一人物名，近期优先。ILIKE 走不了 btree，
但显式 project_id 过滤 + LIMIT 封顶（§14.1 坑 1 / MVP 量级可接受，pg_trgm 列后续）。"""
```

即每次召回都是一次带 `%name%` 的全表扫描，靠 `project_id` 过滤和 `LIMIT` 兜底。

### 降级方案（设计草案，未实施）

现状的「降级」其实是**没有降级**：向量腿失败后剩下一条连触发条件都不明确的弱腿，最坏情况静默返回空。要做的是让降级**可预期、可观测、有真正兜底**：

1. **关键词腿不再依赖 `participants`。** 补一条兜底术语来源：本章目标 / 大纲条目 / 前章摘要的高频实体词。让「无出场人物」不再等于「无召回」。
2. **补索引。** 给 `events.summary` 加 `pg_trgm` GIN 索引（或 `tsvector` 列 + GIN），把 ILIKE 从全表扫变成索引扫。这是纯性能改动，不改语义。
3. **召回统计要能看见。** `recall_stats` 字段已经存在（[contract.py:250](../src/aiink/schemas/contract.py#L250)）且会记录 `vector_hits`/`keyword_hits`/`fused_total`，但空结果时返回 `{}`。建议区分「腿失败」与「腿命中 0」，并在任务详情里暴露出来。
4. **处理 `embeddings` 空表。** 二选一：写一个 backfill 脚本把历史事件补建索引；或者在启用向量召回时先做一次完整性检查，表空就直接走关键词路径并在日志和 UI 上明说。**不能留「开关打开了但什么都没发生」这种状态。**
5. **无前章路径单独设计。** 第 1 章走「世界观 + 大纲 + 卷规划」的静态上下文，明确不期待事件召回。
6. **向量腿失败要升级可见度。** 目前只有 `logger.warning`。至少进 `recall_stats`，让 §16 的召回占比在界面上能反映出「这次是降级跑的」。

## 优先级建议

| 顺序 | 项目 | 理由 | 改动面 |
|------|------|------|--------|
| 1 | 写作阻断（第 1 节） | 阻断性，用户当前完全无法写作 | 网关 + 前端，小 |
| 2 | 召回降级方案（第 4 节） | 直接影响生成质量，且是静默的，越晚发现越难归因 | 后端为主，中 |
| 3 | 事件台账读接口（第 2.1 节） | 25 条数据已存在，只差读出来 | 后端新路由 + 前端新块，中 |
| 4 | 人物状态历史（第 2.2 节） | 数据已完备，压平的只是取数层 | 后端取数 + 前端时间线，中 |
| 5 | 设定实体进提示词（第 3 节） | 会改变生成结果，需要单独回归 | 后端，小改动但影响面大 |

第 5 项**不建议和前面几项混在一起做**：它会改变四个节点的提示词输入，属于「会改变生成输出」的改动，必须能单独回滚和单独评估。
