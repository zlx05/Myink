# 可读性、草稿与邀请制终审

审查时间：2026-09-19。审查对象是当前未提交工作树及
`.local/readability-drafts-invites-review.diff`，不是提交范围。按委托只做静态审查；本审查者没有运行测试、启动服务、提交或修改产品代码。

## Strengths

- 邀请码使用 `secrets.token_urlsafe(32)`，数据库只保存 SHA-256 摘要；过期、撤销和次数均在服务端校验。兑换在 `SELECT ... FOR UPDATE` 后与 `User` 插入及响应构造处于同一事务，重名、响应构造异常和并发竞争都能回滚名额。专项测试覆盖缺失、无效、过期、撤销、重复、并发、重名回滚和明文不落库。
- 建书状态转换使用项目行锁。设定确认、合法大纲写入和 `ready` 晋升在事务内完成；并行设定/大纲提案用同一项目行锁合并 `creation_context`，避免后到提案整块覆盖先到提案。网关在配额扣减和入队前请求 `write=true` 授权，worker 又在真实写作前复查状态。
- 前端把待完成作品与正式作品分开，恢复链接返回向导，已知项目 id 后立即把 id 放入 URL；父流程统一等待两个并行提案，部分失败不会误报“全部成功”。页面明确提示未确认编辑不会保留。
- `--font-ui` 与 `--font-editor` 已分离：界面固定系统无衬线，正文保留宋/楷/黑偏好，新用户正文默认黑体；输入控件继承界面字体，没有通过页面缩放或强制灰阶抗锯齿掩盖问题。
- `ensure_project_creation` 是增量 `ALTER`，默认把存量记录保留为 `legacy_ready`，仅首次升级识别无章节且无大纲的空项目为草稿；代码没有删除或重写作品正文。`legacy_ready` 是兼容旧正文/旧大纲形状的明确豁免，不应按新建作品规则锁死。

## Findings

### P1 — 新书变为 `ready` 后仍可被改写为空大纲而继续写作

当前 [`src/myink/api/routes_book.py`](../../../src/myink/api/routes_book.py) 第 466–477 行只在状态属于 `DRAFT_STATES` 时调用 `validate_creation_outline`。因此新书第一次用合法大纲晋升 `ready` 后，再次 `PUT /outline` 传空对象会跳过校验、覆盖 `volume_outlines`，但状态仍为 `ready`；项目写授权和 worker 随后继续放行。这破坏了“新书处于 ready 时始终有合法大纲”的状态不变量，也给并发的两个大纲确认请求留下了后到非法请求清空先到合法结果的窗口。

应让 `ready` 的每次大纲更新都经过同一验证并在同一项目锁内完成；`legacy_ready` 可继续作为显式兼容豁免。当前 [`tests/test_project_creation.py`](../../../tests/test_project_creation.py) 第 101–107 行已经出现对应回归用例，但审查快照中的产品代码尚未满足它。

### P1 — 创建响应丢失后重试会生成重复草稿，刷新后尤其无法关联服务器结果

[`web/src/pages/NewProjectPage.tsx`](../../../web/src/pages/NewProjectPage.tsx) 第 181–193 行只在 `createProject` 成功返回后才取得项目 id 并写入 `?draft=`；[`src/myink/api/routes_book.py`](../../../src/myink/api/routes_book.py) 第 140–188 行没有接收、持久化或查找建书幂等键。若数据库已提交但响应在途中丢失，页面仍认为创建失败，再提交会插入第二个草稿。刷新会同时丢掉任何仅存在组件内存的请求标识，因此只用 `useRef(randomUUID())` 不能满足计划明确列出的“丢失响应/刷新不重复建书”。

客户端应在账号作用域的会话存储中保留未完成创建请求 id，直到服务器返回项目 id 后再清理；服务端应在用户行锁保护下按 `(user_id, request_id)` 返回原项目，使并发重试也只能创建一行。当前 [`tests/test_project_creation.py`](../../../tests/test_project_creation.py) 第 110–123 行已经增加同 request id 返回同项目的用例，但还需要前端刷新复用同一 id 的回归，且审查快照中的产品代码尚未实现该接口。

### P2 — 增量迁移的“保留旧书”结论缺少直接回归证据

[`src/myink/db.py`](../../../src/myink/db.py) 第 180–194 行的 SQL 静态看是增量且不删行，但当前专项测试没有从旧 schema 构造以下数据并执行迁移：有正文的书、无章节但有大纲的书、无章节且无大纲的书。也没有断言迁移前后项目/章节/大纲行数与正文内容完全不变、只有最后一种状态变为 `draft`。这是本次最敏感的数据安全承诺，不能只由代码阅读或全量业务回归间接证明。

建议增加独立迁移回归，并覆盖第二次执行的幂等性。该项是测试证据缺口；静态审查未发现迁移会删除现有行的实际路径。

### P2 — 创建状态并发与迟到提案的防护已有实现，但测试尚未锁定

[`src/myink/creation.py`](../../../src/myink/creation.py) 第 20–29 行和设定/大纲确认路径通过项目行锁处理并行响应，代码方向正确；但现有六项创建测试是顺序调用，没有证明：设定确认与大纲确认并发时不会越级晋升、两个提案迟到时不会互相丢字段、设定确认后的旧 setup 提案不会覆盖 canon、ready 后迟到提案不会重新写创建上下文。建议用受控 barrier/事件补齐至少一组并发回归，防止以后去掉锁或整块赋值时静默退化。

## Declined to judge

- 未把 `legacy_ready` 缺少现代大纲判为缺陷；这是为保留既有正文可写性的明确兼容策略。终审只要求新状态 `ready` 持续满足新不变量。
- 未评判认证隔离、JWT 轮换、模型凭据、外部请求和容量扩展等更宽风险；这些由另一审查链负责，邀请码本身也不代表生产安全或扩容能力。
- `realm_order` 在恢复向导中的往返格式损失已由主代理确认并处于 TDD 修复中，未重复列为独立发现。
- 未把 CLI 的显式 `--max-redemptions > 1` 选项判为开放注册回退：默认仍是一次，配额、过期和撤销均受服务端约束；如产品语义最终要求所有码绝对一次性，应另行移除该操作员选项。
- 未验证浏览器 computed style、截图、真实数据库迁移或测试结果；委托明确禁止本审查者运行测试和服务。

## Verdict

**CHANGES REQUESTED。** 邀请核销、字体分离、草稿状态锁和双层写作守卫的主体设计可接受；在交付前必须关闭两个 P1：`ready` 新书的每次大纲更新继续验证，以及跨响应丢失/刷新可复用的建书幂等键。迁移保留旧书的专项回归应作为数据安全验收证据补齐。
