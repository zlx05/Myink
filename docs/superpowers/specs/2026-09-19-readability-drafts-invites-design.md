# 可读性、建书草稿与邀请制注册

用户要求修复 Windows 显示器上文字细淡、建书未确认大纲就进入正式书架的问题，并以长邀请码限制新用户数量；同时排查系统风险。沿用自主执行、不提问、不删除数据、不提交和不涉及项目外内容的要求。

## 方案

1. 界面始终使用系统无衬线字体（Windows 优先微软雅黑 UI，macOS 苹方）；正文保留独立宋体/楷体/黑体选择。默认正文黑体，保留用户已选择的正文设置。取消强制灰阶平滑，改善官方主题辅助文字对比度；保留浏览器缩放。不是整站重新设计。
2. 新建项目明确处于 draft 状态，保存创作简报以便恢复；确认设定并确认非空、结构有效的大纲后进入 ready。草稿单独展示“待完成”，链接回建书向导，不混入正式书架。前端不允许跳过；服务端入队检查和 worker 检查阻止 draft 写作。已有正文项目保持可用，已有零章节且无大纲项目可识别为待完成，不删除任何行。确认过的设定和大纲不能因浏览器退出而丢失，未确认提案必须明确提示未保存。
3. 注册必须兑换服务端生成的一次性长随机邀请码（至少 256 位随机性）。数据库只存摘要；支持过期与撤销，兑换和建账号在同一事务内，重复注册/并发兑换不能消耗多个名额。CLI 由服务器操作者发放。已有账号继续密码登录；受邀用户之后登录不重复填写邀请码。不能用一个永久共享口令代替人数控制。不创建公网邀请码管理接口。
4. 风险排查覆盖认证/隔离、创建状态、写作队列/资源限制、模型凭据与外部请求、部署配置。发现但不属于本次修改的风险写入报告，不把邀请码等同于扩容或生产安全认证。

## 验证

先增加失败回归，再实现。字体使用真实主题应用测试和浏览器截图；草稿测试退出恢复、无大纲/空大纲拒绝、状态转换、用户越权、网关不入队；邀请测试缺失/错误/过期/重复/并发兑换、失败回滚、已有账号登录。全套 Python/Go/Web 检查仅连接独立测试服务；本地重建并更新应用容器，保留用户数据与所有卷。
